# FlyMater Routing

Управляемые из GitHub правила для AWG Manager (Keenetic/Netcraze), Shadowrocket (iPhone/macOS), Throne (Windows 11).

## 1. Публикация

1. В публичном репозитории разместите файлы проекта в ветке `main`, включая папку `.github/`.
2. Включите GitHub Actions. В **Settings → Actions → General → Workflow permissions** выберите **Read and write permissions**, чтобы сборка могла сохранять результаты. Правила ветки должны разрешать запись от GitHub Actions и владельца токена панели.
3. В **Settings → Pages** выберите **Deploy from a branch → main → /docs**. После развёртывания откройте [панель каталогов FlyMater](https://flymater.github.io/flymater-routing/). Панель, опубликованные правила, черновики проверок и подписки доступны для чтения без авторизации.

## 3. Подключение AWG Manager 2.16.5

Маршрутизация → NDMS → Создать вручную → название `FlyMater PROXY` → «Подписки»: добавьте URL `awg/proxy.txt` → маршрут: нужный AWG-туннель → сохранить и включить. Настройки → Автообновление подписок DNS: 24 часа. Клиентам нужно использовать DNS роутера. NDMS не обеспечивает такую же очередность DIRECT/PROXY, как sing-box; при конфликтующих правилах проверьте фактический маршрут. Если настроен альтернативный движок, у него другие опции.

Для **sing-box Router** добавьте три remote rule sets по ссылкам PROXY, DIRECT и REJECT из раздела 2. Выберите формат binary и интервал обновления. Привяжите PROXY к нужному туннелю, DIRECT к прямому выходу, а REJECT к блокировке. Примените настройки на роутере.

## 4. Shadowrocket на iPhone/macOS

В разделе Configuration/Config добавьте удалённый конфигурационный файл по URL `shadowrocket/flymater.conf`, выберите его активным и проверьте, что политика PROXY использует выбранный вами VPN-узел. В версиях и локализациях Shadowrocket названия меню могут отличаться. Не добавляйте CONF как подписку VPN-серверов. Обновление зависит от настроек приложения; при необходимости обновите конфигурацию вручную.

## 5. Throne 1.3.2 на Windows 11

Используйте **удалённый профиль маршрутизации**, а не подписку на прокси-серверы. В `Routing` → `Routing Settings` → `Route` найдите добавление удалённого профиля маршрутизации и укажите URL `throne/flymater.json`. Если удобнее, используйте глубокую ссылку `throne://remoteroute/<base64>` (Base64 из строки `URL#FlyMater Routing`). Выберите профиль активным. В разделе `Basic Settings` → `Subscription` включите `Routing profiles auto update` (по умолчанию выключено). Обновление можно запускать вручную в разделе маршрутизации; после обновления перезапустите подключение для применения правил.

Встроенные стандартные proxy/direct/block должны работать с твоим выбранным сервером. В режиме TUN убедитесь, что DNS перехватывается корректно, иначе доменные правила могут не срабатывать.

## 6. Редактирование

Вручную редактируйте `source/local.txt`, `source/proxy.txt`, `source/direct.txt`, `source/reject.txt`: по одному домену в строке, без `DOMAIN-SUFFIX`, `https://`, `*.`, inline-комментариев. Меняйте в GitHub и жмите Commit. Сгенерированные файлы не редактируйте.

### Панель каталогов

GitHub Actions ежедневно в 06:27 по Москве проверяет наборы SagerNet Geosite и обновляет примеры доменов в описаниях. При открытии панели и по кнопке **Обновить каталог** обе колонки получают последнюю подготовленную версию. Для нового набора описание строится по его доменам. Название сервиса и пояснение о его назначении можно уточнить в `docs/geosite.js`. Чтобы обновить примеры раньше, запустите workflow **Обновить описания Geosite** вручную.

1. Выберите каталог SagerNet Geosite или GeoIP. Найдите набор по названию, тегу или синониму. Например, `Telegram`, `geosite-telegram` и «Телеграм» найдут один набор. В GeoIP можно искать страну по-русски: «Россия» найдёт `geoip-ru`. Для неизвестных названий панель показывает полный технический тег. Нажмите **Добавить**. Можно добавить папку GitHub вида `https://github.com/OWNER/REPO/tree/BRANCH/folder` (имя ветки без слешей), собственный HTTPS JSON-индекс или прямой URL набора. Для просмотра индекса его сервер должен разрешать запросы браузера с GitHub Pages (CORS).
2. Для каждого набора выберите маршрут и устройства. Кнопкой **Переименовать** можно задать своё название, в том числе для набора по ссылке. Оно сохраняется при публикации и имеет приоритет при обновлении каталога. Чтобы вернуть исходное название, очистите поле. NDMS получает только PROXY. Введите fine-grained GitHub-токен для этого репозитория с **Contents → Read and write**. Панель держит токен в памяти вкладки.
3. Нажмите **Проверить черновик**. Панель сохранит запрос в `preview/request.json`. Actions проверит источники и форматы и запишет результат. Для каждого выбранного клиента отчёт показывает покрытие и пропущенные условия. Частичное покрытие допускает публикацию. Если подходящих правил нет, набор не попадёт в подписку этого клиента. Конфликты маршрутов и ошибки загрузки блокируют публикацию. Если открыты две вкладки, новая проверка может вытеснить старую. При конфликте сохранения загрузите актуальные настройки и повторите свои изменения.
4. Нажмите **Опубликовать** и дождитесь успешной сборки подписок в нижнем блоке. Сохранение настроек и обновление подписок — отдельные операции. Новая сборка читает источники заново. Если источник недоступен или найден конфликт маршрутов, остаётся доступной последняя успешная сборка.
5. Обновление внешних источников происходит при публикации и ежедневно в 03:17 UTC. Запустить сборку вручную можно в **Actions → Generate routing profiles → Run workflow**. Устройства применяют файлы при следующем обновлении своей подписки.

В своём JSON-индексе укажите уникальный тег и URL каждого набора. Необязательное поле `name` задаёт название для показа и поиска в панели.

```json
{"sets":[{"tag":"telegram","name":"Мессенджер Telegram","url":"https://raw.githubusercontent.com/SagerNet/sing-geosite/rule-set/geosite-telegram.srs"}]}
```

Ручные списки продолжают участвовать в сборке. При переносе сервиса между маршрутами устраните совпадения с ручными списками, указанные проверкой. Для внешних наборов переносимыми условиями служат точный домен, доменный суффикс и IP/CIDR. В NDMS точный домен требует исключения клиента. Сложные условия sing-box можно оставить только для sing-box. Внешние правила с ведущей точкой у суффикса требуют отдельной проверки представимости.

### Локальная сборка

Из корня проекта создайте проектное окружение `python3 -m venv .venv`. Установите официальный sing-box **1.12.0** в PATH либо задайте переменную `SING_BOX` с путём к бинарному файлу. Запустите `.venv/bin/python scripts/generate.py`. Для тестов маршрутизации используйте `.venv/bin/python -m unittest discover -s tests -p test_routing.py -v`. Для локального просмотра панели запустите `.venv/bin/python -m http.server 8000 --bind 127.0.0.1` и откройте `http://127.0.0.1:8000/docs/`. Запись в GitHub доступна в опубликованной панели.

## Ограничения и безопасность

- Это подписки **на правила**, а не конфигурации VPN и не список ключей/серверов. Не публикуйте ключи, токены или конфигурации с секретами.
- Начальные списки — неполные примеры: вручную перенесите все ваши действующие домены, затем тестируйте на каждом клиенте.
- Политика блокировки `reject` используется после `direct` согласно схеме приоритетов; при необходимости переместите выше.
- RAW NDMS у AWG Manager принимает домены и CIDR; ручные списки принимают домены, подключённые наборы также поддерживают CIDR.
- Прохождение обновления GitHub Actions не гарантирует работоспособность на конкретной версии клиента: проверяйте логи и тестовые домены.
